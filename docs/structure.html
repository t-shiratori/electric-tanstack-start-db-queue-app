リポジトリは、ブラウザで動く app/、API サーバーの server/、DB 定義の migrations/ と各種設定ファイルで構成されています。 ここでは、どのファイルが何を担当し、どう依存し合っているかを整理します。

app と server で共有しているコード
  • shared/schemas.ts：Zod スキーマ。実行環境に依存しない（import.meta.env や pg を参照しない）ため、ブラウザと Node.js の両方から読み込めます。
  • app/domain/entry：状態遷移の判定（checkEventAppend）。ドメイン層はフレームワークに依存しない純粋なコードなので、サーバーも同じルールで検証するために読み込んでいます。

04各レイヤーの責務

Routes

URL と画面の対応付け。画面を <ClientOnly> で包み、ブラウザでだけ描画させる。ロジックは持たない。

Components

画面の描画と操作の受付。フックでデータを受け取り、ボタン操作でユースケースを呼ぶ。持つのは UI の状態（選択中の人数など）だけ。

Query

コレクションに対するライブクエリと、そこから派生するビューを React のフックとして提供する。

Usecases

「整理券を発行する」「呼び出す」など 1 つの操作の手順。ID・トークンの生成、リポジトリの呼び出し、結果の返却を行う。

Domain

型・定数・状態の計算・遷移ルール・リポジトリのインターフェース。React や TanStack DB には依存しない純粋なコード。

Infrastructure

外部とのつなぎ込み。コレクション定義（Electric・tRPC）、リポジトリ実装、Zod スキーマ、マッパー、環境変数。

05モジュールの依存関係

矢印は「import している」方向です。中心のドメイン層には多くの矢印が入りますが、ドメイン層から外へ出る矢印はありません。

  • 依存性の注入：ユースケースはリポジトリのインターフェース（domain）だけを知り、実装は画面が getEntryRepository() などのファクトリーで取得して引数で渡します。
  • 例外：getNextTicketNumber だけはリポジトリを介さず、ユースケースから tRPC クライアントと Zod スキーマ（infrastructure）を直接使っています。
  • サーバーとの境界：app/client/trpc.ts は import type { AppRouter } でサーバーの型だけを取り込みます。ビルド時に型は消えるため、サーバーのコードはブラウザに含まれません。
  • サーバーから見た依存：server/ は shared/schemas.ts（入力の検証）と app/domain/entry（状態遷移の判定）だけを読み込みます。どちらも実行環境に依存しないコードです。

ユースケースの呼び出し関係

状態を変える 4 つの操作は、すべて共通の addEntryEvent() にイベントの種類と操作者を渡すだけの薄いラッパーです。addEntryEvent() はリポジトリの findByEntryId() で取得したローカルのイベント履歴を使い、checkEventAppend() で遷移ルールを検証してから書き込みます。
