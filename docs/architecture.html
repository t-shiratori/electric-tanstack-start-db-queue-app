Architecture

アプリ全体のアーキテクチャ

このアプリは、ブラウザ・リバースプロキシ・2 つの Node.js プロセス・2 つの Docker コンテナで動きます。 最大の特徴は、書き込みは tRPC、読み取りは Electric と経路を分け、ブラウザ内の TanStack DB がその 2 つを束ねている点です。

02読み取りと書き込みの分離

データは 「画面 → tRPC → PostgreSQL → Electric → 画面」 という一方向のループを回ります。 画面がデータを取得するために API を呼ぶことはなく、書き込みの結果も Electric 経由で戻ってきます。

書き込み経路（Command）

  • コレクションの insert() から始まる
  • onInsert ハンドラが tRPC のミューテーションを呼ぶ
  • サーバーは INSERT とともにトランザクション ID（txid）を返す
  • 失敗したら楽観的な変更はロールバックされる

読み取り経路（Query）

  • ブラウザは Shape を購読し続けるだけ（API を呼ばない）
  • 自分の書き込みも他端末の書き込みも同じ経路で届く
  • 届いた変更でライブクエリが差分だけ再計算される
  • 画面は React のフックとして結果を受け取る

03シーケンス：整理券の発行

受付端末で「整理券を発行」を押してから、モーダルが表示され、他の端末にも反映されるまでの流れです。

  1. 1仮の番号：画面に即時表示するための番号をサーバーの MAX(number) + 1 で取得する。
  2. 2entry の書き込み：コレクションに仮の番号で insert した瞬間に画面へ反映される。サーバーは待ち行列の行をロックして確定番号を採番し INSERT する。Electric から同じ txid が届いたら確定（同期された確定番号に置き換わる）。
  3. 3イベントの書き込み：created イベントを同じ方法で書き込む。サーバーは状態遷移ルールを検証してから INSERT する。
  4. 4結果の表示：確定番号とトークンで QR コード付きのモーダルを表示する。他の端末にはステップ 2・3 の Electric の配信で反映済み。

04シーケンス：呼び出しが全端末に届くまで

呼び出し端末で「呼び出す」を押すと、1 件の called イベントが追記され、それが全端末に配られます。各端末はそれぞれ自分で状態を計算し直します。

05フロントエンドのレイヤー構成

app/ 配下はクリーンアーキテクチャを参考にした層に分かれています。依存は外側から内側へ向かい、 中心のドメイン層はどのフレームワークにも依存しません。

06起動とプロセス

caddy runHTTPS の入口を開く（Caddyfile は pnpm generate:caddy で生成）
docker compose up -dPostgreSQL と Electric を起動（Electric は DB の healthcheck 後）
pnpm devpnpm run --parallel "/^dev:/" で dev:client と dev:server を同時起動
tRPC サーバーが起動していないと…

Vite のログに http proxy error: /trpc/… ECONNREFUSED が出て、整理券の発行などの書き込みが失敗します。 画面の表示（Electric による読み取り）は動き続けるため、気づきにくい点に注意してください。

07アーキテクチャ上の判断

判断理由トレードオフ
読み取りは Electric、書き込みは自前 APIElectric は読み取り専用の同期エンジン。書き込みのルール（検証・採番）はサーバーで持てる経路が 2 つになり、書き込み後に「同期で戻るまで待つ」仕組み（txid）が必要
書き込み API を独立した Hono + tRPC サーバーにしたTanStack Start のサーバー関数から移行。API を画面フレームワークから切り離し、型安全なまま単体で動かせる起動するプロセスが増え、ポートとプロキシの設定が必要
状態は各端末で計算するイベントの追記だけで済み、同時操作に強い。サーバーに集計ロジックが不要全端末が全データを同期する必要がある
画面はブラウザでのみ描画（ClientOnly）コレクションと同期はブラウザでしか動かないSSR による初期表示の高速化は得られない
開発環境でも HTTPS（Caddy）crypto.randomUUID() に安全なコンテキストが必要。LAN 内のスマホからも使う自己署名証明書の警告を初回に許可する必要がある
