1.概要

1.1目的

飲食店・クリニック・窓口などで使う整理券式の順番待ちを、複数の端末でリアルタイムに共有できる Web アプリとして提供します。

  • 受付・呼び出し・掲示・お客様の確認を、同じ Web アプリの画面として提供する
  • ある端末での操作が、他のすべての端末に即座に反映される
  • 状態の変化をすべて履歴として残し、現在の状態は履歴から求める

1.2対象範囲

区分内容
対象待ち行列 1 つ（デフォルト店舗）での受付・呼び出し・完了・スキップ・キャンセル、状況の掲示、お客様スマホでの状況確認、QR コードによるスマホ連携
対象外認証・権限管理、複数の待ち行列、SMS / プッシュ通知、管理画面、統計ダッシュボード、本番環境へのデプロイ

1.3想定する利用シーン

来店・受付スタッフが受付端末で人数を選び、整理券を発行する
QR を渡すお客様が QR を読み取り、スマホで順番を確認する
呼び出しスタッフが呼び出し端末で次の番号を呼ぶ。掲示とスマホに即反映
対応来たら「完了」、来なければ「スキップ」
取り消しお客様はスマホから自分でキャンセルできる

6.機能仕様

F-01整理券の発行

受付端末actor: staffcreateEntry() / getNextTicketNumber()
概要
新しい受付を作り、整理券番号・QR コード・トークンを表示する
入力
人数（1〜6）
事前条件
tRPC サーバーに接続できること（採番と書き込みに必要）
処理
  1. tRPC queue.getNextTicketNumber で仮の番号（最大番号 + 1）を取得する
  2. 受付 ID（UUID v4）と 8 文字のトークンを生成する
  3. entry を仮の番号で書き込む（画面に即時反映）。サーバーは待ち行列の行をロックして確定番号を採番し、INSERT する。確定（Electric で同期が戻る）まで待つ
  4. entry_event に created（actor: staff, device_id: null）を書き込み、確定まで待つ
  5. QR コード画像を生成し、確定番号で発行完了モーダルを表示する
事後条件
受付が「待機中」となり、全端末の待機リストに表示される。同時に発行されても番号は重複せず、両方とも成功する
エラー
番号取得失敗：「番号取得エラー: …」／書き込み失敗：「エントリー作成エラー: …」／その他：「エントリー作成に失敗しました」をアラート表示
F-02〜F-05 に共通する状態遷移の検証

状態を変える操作は、書き込む前にクライアント（ローカルのイベント履歴）で、書き込み時にサーバー（DB のイベント履歴、受付の行をロック）で、7.1 の遷移ルールに合うかを検証します。 合わない場合は記録せず、「現在の状態（○○）からはこの操作を実行できません」というメッセージで各機能のエラーとして表示します（例：「完了処理エラー: 現在の状態（キャンセル済み）からはこの操作を実行できません」）。

F-02呼び出し

呼び出し端末actor: staffcallEntry()
概要
待機中の先頭（番号が最も小さい）受付を呼び出す
事前条件
待機中の受付が 1 件以上ある
処理

事後条件
状態が「呼び出し中」になり、表示端末の「呼び出し中」とお客様スマホに反映される
エラー
対象なし：「呼び出せるエントリーがありません」／失敗：「呼び出しエラー: …」

F-03完了

呼び出し端末actor: staffmarkEntryDone()
概要
呼び出し中の受付の対応を完了する
事前条件
対象が「呼び出し中」（ボタンは呼び出し済みリストにのみ表示）
処理
entry_event に done を書き込む
事後条件
状態が「完了」になり、完了件数と平均待ち時間に反映される
エラー
「完了処理エラー: …」

F-04スキップ

呼び出し端末actor: staffskipEntry()
概要

状態が「スキップ」（終了状態）になり、呼び出し済みリストから消える
エラー
「スキップエラー: …」

F-05キャンセル

スマホ画面actor: usercancelEntry()

エラー
「キャンセルエラー: …」

F-06状況の表示

受付端末表示端末useQueueStats() / useCalledEntries()

全画面ElectricSQL + TanStack DB

8.集計仕様

項目算出方法表示
待機中状態が waiting の受付の件数受付・表示
呼び出し中状態が called の受付の件数受付・表示
完了状態が done の受付の件数受付
平均待ち時間（分）状態が done の受付について「最新イベント（done）の時刻 − 受付時刻」の平均。done が 0 件なら 0受付（小数 1 桁）・表示（整数）
待ち順位（スマホ）待機中の受付を番号順に並べたときの位置（1 始まり）スマホ

平均待ち時間は「受付から完了まで」の時間で、呼び出し後の対応時間も含みます。また、集計は同期されているすべての受付が対象で、日付による区切りはありません。 件数はすべて「受付の件数（組数）」で、人数（party_size）は集計に使っていません。

9.2入力値の検証

Zod スキーマでクライアント（コレクション）とサーバー（tRPC 入力）の両方で検証します。スキーマは shared/schemas.ts に 1 か所だけ定義し、両方から読み込みます。

項目ルール
id / queue_id / entry_idUUID 形式
number正の整数（tRPC の入力には含めず、サーバーで採番）
party_size正の整数（省略時 1）
public_tokenちょうど 8 文字、A–Z と 0–9 のみ
typecreated / called / done / skipped / cancelled のいずれか
actorstaff / system / user のいずれか
device_id文字列または null
created_atクライアントでは Date。サーバーへの入力には含めない（サーバーで now()）

10.API 仕様

10.1tRPC プロシージャ

エンドポイントは /trpc。クライアントは httpBatchLink を使うため、URL に ?batch=1 が付き、入力は {"0": …} の形で送られます。

プロシージャ種類HTTP入力出力
queue.getNextTicketNumberqueryGET待ち行列 ID（UUID）{ number: number }
entry.insertmutationPOST{ id, queue_id, party_size, public_token }（番号はサーバーで採番）{ txid: number, number: number, success: true }

例：次の整理券番号の取得
// リクエスト
GET /trpc/queue.getNextTicketNumber?batch=1&input={"0":"a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11"}

// レスポンス
[{ "result": { "data": { "number": 35 } } }]
例：受付の書き込み
// リクエスト
POST /trpc/entry.insert?batch=1
{ "0": { "id": "…uuid…", "queue_id": "a0eebc99-…", "party_size": 2, "public_token": "XTVLLPU2" } }

// レスポンス（number は確定した整理券番号、txid は PostgreSQL のトランザクション ID）
[{ "result": { "data": { "txid": 1234, "number": 35, "success": true } } }]
  • txid：INSERT と同じトランザクション内で pg_current_xact_id() を取得した値。クライアントは Electric から同じ txid の変更が届くまで待つ
  • 採番：entry.insert は待ち行列の行を FOR UPDATE でロックし、MAX(number) + 1 で採番してから INSERT する
  • 状態遷移の検証：entry.insertEvent は受付の行を FOR UPDATE でロックし、既存のイベントから求めた状態に対して遷移ルールを検証する

11.非機能仕様

分類仕様
即時性操作した端末では楽観的更新によりサーバー応答を待たずに表示を更新する
リアルタイム性他の端末へは Electric のロングポーリングで配信される。手動の再読み込みは不要
同時操作状態変更はイベントの追記のみのため、行の上書きは起きない。同じ受付への同時操作はサーバーで受付の行をロックして直列化し、遷移ルールに合わないものは拒否する。同時発行は待ち行列の行のロックで直列化し、番号の重複なく両方成功する
オフライン同期済みのデータの表示は継続するが、書き込み（発行・呼び出し等）はできない。データはメモリ上にあり、再読み込みすると再同期が必要
通信の安全性ブラウザからのアクセスは Caddy による HTTPS（開発用の自己署名証明書）。VITE_ELECTRIC_URL は https のみ許可
対応ブラウザcrypto.randomUUID() が使える最新のブラウザ（安全なコンテキストが必要）
画面サイズスタッフ画面はタブレット・PC（大画面で 2 カラム）、スマホ画面は縦長の 1 カラム
ログtRPC サーバーが整理券発行・イベント記録の内容と txid をコンソールに出力する

13.制約事項・今後の拡張

制約事項

  • 待ち行列はデフォルト店舗 1 つのみ（ID は受付端末のコードに固定）
  • 認証がなく、URL を知っていればどの画面も開ける
  • オフラインでは整理券の発行・呼び出しなどの書き込みができない
  • 全端末が全受付のデータを同期する（スマホも他のお客様の受付情報を受信している）
  • スマホ画面は同期が完了するまで一時的に「エントリーが見つかりません」と表示されることがある
  • 受付のデータは削除されず、集計は全期間が対象

今後の拡張案

  • SMS / プッシュ通知による呼び出し通知
  • 複数の待ち行列と店舗設定の管理画面
  • 営業日ごとの集計・統計ダッシュボード
  • スタッフ画面の認証（PIN など）
  • オフライン書き込みとデータの永続化
