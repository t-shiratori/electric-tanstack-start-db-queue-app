マテリアライズドビュー解説

このアプリは受付の「状態」を保存せず、イベントの履歴から毎回計算します。 その計算結果を画面にすぐ渡せる形で持っておくしくみが、このアプリでいうマテリアライズドビューです。 一般的な DB の機能とどう違うのか、なぜブラウザ側で作るのか、どう組み立てて更新しているのかを解説します。

01マテリアライズドビューとは

データベースのビュー（VIEW）は「保存されたクエリ」で、参照するたびに元のテーブルから計算されます。 マテリアライズドビュー（MATERIALIZED VIEW）は、その計算結果を保存しておき、すぐに読めるようにしたものです。 このアプリでは、同じ考え方をブラウザ内のライブクエリで実現しています。

このアプリのコードやコメントで「マテリアライズドビュー」と呼んでいるのは、PostgreSQL の MATERIALIZED VIEW ではなく、TanStack DB のライブクエリと、そこから派生させた React のフックのことです。DB にビューは作っていません。

02なぜビューが必要なのか

このアプリはイベントソーシングを採用しており、データベースには「事実」だけが保存されています。 画面が欲しいのは「いま待機中の受付はどれか」といった解釈なので、事実から解釈を作る層が必要になります。それがビューです。

保存しないことの利点

  • 「状態の列」を取り合う競合が起きない（書き込みは追記だけ）
  • ビューの計算方法を変えても、データの移行が要らない
  • どの端末も同じ事実から同じ計算をするので、結果が一致する

そのぶん必要になること

  • 計算のコストを抑える工夫（差分更新・メモ化）
  • 計算に必要な事実をすべて手元に持っておくこと（同期）
  • 計算ロジックを 1 か所にまとめておくこと（ドメイン層）

03どこで作るか：サーバーかクライアントか

PostgreSQL に MATERIALIZED VIEW を作ってそれを同期する方法も考えられますが、このアプリでは採用していません。

観点サーバー側（MATERIALIZED VIEW）クライアント側（ライブクエリ）
同期との相性Electric はテーブルの変更を配信するため、ビューの結果をそのまま同期できない同期されたテーブルの行から作るので、そのまま使える
鮮度REFRESH するまで古い。誰がいつ REFRESH するかの設計が必要データが届いた瞬間に自動で更新
楽観的更新サーバーで確定するまで反映されない操作した瞬間の未確定の変更もビューに入る
計算する場所サーバー 1 か所各端末（全端末が同じロジックで計算）
向いている用途大量データの集計、日次・月次のレポートなど確定値画面の状態、一覧、件数など UI 向けの軽い計算

04このアプリのビューの構造

ビューは 4 つの層を順に通って作られます。下の層ほど汎用的で、上の層ほど特定の画面向けです。

app/query/entry/hooks.ts（派生ビューの例）
// 層 4：useEntryStates の結果をさらに絞り込む・並べ替える
export function useEntriesByState(state: EntryState) {
  const entryStates = useEntryStates();
  return useMemo(() => entryStates.filter((e) => e.state === state), [entryStates, state]);
}

export function useWaitingEntries() {
  const waiting = useEntriesByState('waiting');
  return useMemo(() => [...waiting].sort((a, b) => a.ticketNumber - b.ticketNumber), [waiting]);
}

export function useNextWaitingEntry() {
  return useWaitingEntries()[0];   // 次に呼ぶのは待機中の先頭
}

05ビューが更新される流れ

呼び出し端末で 30 番を呼び出したとき、各端末のビューがどう更新されるかを追います。

  • 層 2（ライブクエリ）は、増えた 1 行の影響だけを計算します。データが増えても更新のコストはほとんど変わりません。
  • 層 3（共有ストア）は、層 2 の結果が変わるたびに全受付について状態を計算し直します。ただし計算するのは変更 1 回につき 1 回だけで、何個のフックが使っていても増えません。
  • 層 4（useMemo）は、各フックが層 3 の結果から絞り込み・並べ替え・集計をやり直します。受付が数百件程度なら問題になりませんが、件数が増えると効いてきます（08 改善案）。

06楽観的更新とビュー

ライブクエリは「同期済みのデータ ＋ 未確定の楽観的な変更」を入力にします。そのため、操作した端末ではサーバーの応答を待たずにビューが変わり、 失敗した場合は楽観的な変更が取り消されてビューも元に戻ります。

「呼び出す」entryEventsCollection.insert(called)
即時未確定の called がコレクションに入り、ビューが「呼び出し中」に
サーバー遷移ルールを検証して INSERT。txid を返す
確定Electric から同じ txid の行が届き、未確定の行と置き換わる（ビューは変わらない）
失敗時未確定の行が消え、ビューが「待機中」に戻る

楽観的な行と同期済みの行は同じ ID なので、確定の瞬間に行が二重になったり消えたりしません。ビューの側では楽観的かどうかを意識する必要がない、というのがこの組み合わせの強みです（詳しくはTanStack DB × Electric の txid の解説）。

07ビューを作るときのルール

やってよいこと

  • コレクションからの JOIN・絞り込み・並べ替え
  • 状態の導出（ロジックはドメイン層の関数を呼ぶ）
  • 件数・平均などの軽い集計
  • 既存のビューを組み合わせた新しいビュー

やってはいけないこと

  • ビューの結果をコレクションや DB に書き戻す（状態を保存することになる）
  • ビューの中で状態の判定ロジックを独自に書く（端末ごとに結果がずれる原因）
  • 大量データの重い集計（サーバー側の仕事）
  • ビューの結果だけで書き込みの可否を確定させる（最終判定はサーバー）

新しいビューを追加する例

「人数の合計（待機中）」を表示したい場合は、既存のビューから派生させます。

追加例（イメージ）
export function useWaitingPeopleCount(): number {
  const waiting = useWaitingEntries();
  return useMemo(() => waiting.reduce((sum, e) => sum + e.partySize, 0), [waiting]);
}

08現状の課題と改善案

1 画面で同じライブクエリが複数作られる（対応済み）

以前は、派生ビューがそれぞれ内部の useEntryStates() で useLiveQuery を呼んでいたため、1 つの画面で複数のビューを使うと 同じ JOIN のライブクエリと状態の計算がフックの数だけ行われていました（例：呼び出し端末では 3 回）。 スマホ画面の useEntryByToken も、別に専用のライブクエリを作っていました。

現在は app/query/entry/entry-states-store.ts で共有のライブクエリを 1 つだけ作り、状態の計算も変更 1 回につき 1 回だけ行います。 useEntryByToken も共有の結果から探す形にしたので、どの画面でも JOIN は 1 つです（04 コードで追う）。

共有のライブクエリを各フックから useLiveQuery(共有コレクション) で読む方法もありますが、それでは JOIN は 1 つになっても、Zod の検証と状態の計算はフックごとの useMemo で行われ、重複が残ります。そのため、状態の計算結果までまとめて持つ小さなストアを作り、useSyncExternalStore で配る形にしています。React Context でも同じことはできますが、ルートに Provider を置く必要がなく、フックの使い方も変わらないこの形を選びました。
