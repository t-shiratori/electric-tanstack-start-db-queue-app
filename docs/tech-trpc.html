tRPC 技術解説

tRPC は、サーバーに定義した関数（プロシージャ）を、クライアントから型付きの関数呼び出しとして使えるようにするライブラリです。 このアプリでは、Electric が担当できない書き込みと採番を、Hono 上で動く tRPC サーバーが受け持っています。

@trpc/server・@trpc/client 11.29.5 hono 4.13.19 @hono/trpc-server 0.4.2 zod 4.6.7

01tRPC とは

REST API では、サーバーとクライアントの間で「URL・リクエストの形・レスポンスの形」を別々に定義し、ずれないように管理する必要があります。 tRPC では、サーバーのコードの型そのものをクライアントが参照するため、スキーマファイルやコード生成なしで両者がつながります。

RESTURL と JSON の約束事

const res = await fetch('/api/entries', {
  method: 'POST',
  body: JSON.stringify(data),
});
const json = await res.json(); // 型は any
  • URL の打ち間違いは実行するまで分からない
  • レスポンスの型は自分で書く（ずれても気づけない）

tRPC関数呼び出しとして使う

const result = await trpc.entry.insert.mutate({
  id, queue_id,
  party_size, public_token,
});
result.number; // number 型と推論される
  • プロシージャ名・入力の形が補完され、間違いはコンパイルエラー
  • サーバーの戻り値の型がそのままクライアントに伝わる

02このアプリでの役割

tRPC が受け持つのは、PostgreSQL への書き込みと採番の 3 つのプロシージャだけです。画面に表示するデータの取得には使いません（それは Electric の役目です）。

03サーバー側の組み立て

サーバーは「初期化 → プロシージャ → ルーター → HTTP への接続」の順に組み立てられています。

server/trpc/init.ts ・ server/trpc/context.ts
// 初期化：コンテキストの型を指定して tRPC インスタンスを作る
const t = initTRPC.context<Context>().create();
export const router = t.router;
export const publicProcedure = t.procedure;

// コンテキスト：リクエストごとに呼ばれ、プロシージャから ctx.pool で使える
export function createContext(_opts, _c): Context {
  return { pool };
}
server/routers/queue.ts
export const queueRouter = router({
  getNextTicketNumber: publicProcedure
    .input(UuidSchema)                         // ① 入力を Zod で検証
    .query(async ({ input: queueId, ctx }) => {   // ② query = 読み取り系
      const result = await ctx.pool.query(
        'SELECT COALESCE(MAX(number), 0) as max_number FROM entry WHERE queue_id = $1',
        [queueId],
      );
      return { number: (result.rows[0]?.max_number || 0) + 1 }; // ③ 戻り値の型が推論される
    }),
});
server/trpc/router.ts
export const appRouter = router({
  entry: entryRouter,   // trpc.entry.insert / trpc.entry.insertEvent
  queue: queueRouter,   // trpc.queue.getNextTicketNumber
});

export type AppRouter = typeof appRouter;  // ← クライアントが使うのはこの「型」だけ

04型がクライアントに届くしくみ

tRPC の要は export type AppRouter = typeof appRouter です。クライアントは import type でこの型だけを取り込み、 プロシージャ名・入力・出力の型を推論します。import type はビルド時に消えるため、サーバーのコードはブラウザに一切含まれません。

app/client/trpc.ts
import { createTRPCClient, httpBatchLink } from '@trpc/client';
import type { AppRouter } from '../../server/trpc/router';  // 型だけ

export const trpc = createTRPCClient<AppRouter>({
  links: [httpBatchLink({ url: '/trpc' })],   // 同じオリジンの /trpc に送る
});
React のフックではなく「バニラ」クライアントを使う理由

tRPC の呼び出し元はコレクションの onInsert とユースケースで、どちらも React コンポーネントの外です。そのため React Query 連携ではなく、 普通の関数として呼べる createTRPCClient を使っています（そのため React Query 連携の @trpc/tanstack-react-query は依存に含めていません）。

05リクエストの中身

tRPC は独自のプロトコルではなく、ふつうの HTTP と JSON でやり取りします。ブラウザの開発者ツールで中身をそのまま確認できます。

種類HTTPURL入力の場所
queryGET/trpc/queue.getNextTicketNumber?batch=1&input=…クエリ文字列（URL エンコードした JSON）
mutationPOST/trpc/entry.insert?batch=1リクエストボディ（JSON）
query の例（実際に受付端末が送るリクエスト）
GET /trpc/queue.getNextTicketNumber?batch=1&input=%7B%220%22%3A%22a0eebc99-…%22%7D
                                                   ↑ {"0":"a0eebc99-…"} をエンコードしたもの

// レスポンス（バッチなので配列）
[{ "result": { "data": { "number": 35 } } }]

エラーの伝わり方

原因tRPC のエラーコードクライアントでの見え方
入力が Zod の検証に失敗（例：トークンが 7 文字）BAD_REQUESTTRPCClientError が throw される
待ち行列・受付が存在しないNOT_FOUND同上
状態遷移ルールに合わない（例：キャンセル済みの受付を完了）CONFLICT同上（メッセージ「現在の状態（○○）からはこの操作を実行できません」）
その他の SQL の失敗（例：トークンの重複）INTERNAL_SERVER_ERROR同上
サーバーに接続できない（未起動など）―ネットワークエラー（Vite のログに ECONNREFUSED）

いずれも onInsert から例外が投げられるため、TanStack DB のトランザクションは failed になり、楽観的な変更はロールバックされます。ユースケースはそのエラーメッセージを画面のアラートに表示します。

06Hono との統合

tRPC 自体は HTTP サーバーを持たないため、Hono の上に @hono/trpc-server のミドルウェアとして載せています。Node.js での起動には @hono/node-server を使います。

server/index.ts（抜粋）
const app = new Hono();

app.use('/trpc/*', cors({ origin: ['http://localhost:5173', 'https://localhost:5173'], credentials: true }));
app.use('/trpc/*', trpcServer({ router: appRouter, createContext }));   // tRPC をマウント
app.get('/health', (c) => c.json({ status: 'ok' }));                  // ヘルスチェック

const port = Number(process.env.TRPC_PORT) || 3001;
serve({ fetch: app.fetch, port });
  • なぜ Hono か：軽量で Web 標準（Fetch API）ベースのため、tRPC の fetch アダプターとそのまま組み合わせられます。/health のような tRPC 以外のエンドポイントも同じサーバーに置けます。
  • CORS：開発時は Vite のプロキシ経由で同一オリジンになるため、通常は CORS は使われません。tRPC サーバーに直接アクセスする場合の備えです。
  • 起動：tsx watch --env-file=.env server/index.ts。ファイルを保存すると自動で再起動し、.env から DATABASE_URL などを読み込みます。

09プロシージャを追加する手順

例として「待ち行列の状態を取得する」プロシージャを追加する場合の流れです。

スキーマshared/schemas.ts に入力の Zod スキーマを用意
プロシージャserver/routers/queue.ts に publicProcedure.input(…).query(…) を追加
ルーター新しいルーターなら server/trpc/router.ts に登録
呼び出しtrpc.queue.xxx.query(…) がすぐ補完される
例：server/routers/queue.ts に追加
const QueueStatusRowSchema = z.object({ status: z.enum(['open', 'closed']) });

getQueueStatus: publicProcedure
  .input(UuidSchema)
  .query(async ({ input: queueId, ctx }) => {
    const result = await ctx.pool.query('SELECT status FROM queue WHERE id = $1', [queueId]);
    // DB の行は型が付かないので、as ではなく Zod で検証して型を付ける
    return QueueStatusRowSchema.parse(result.rows[0]);
  }),

// クライアント側（型は自動で付く）
const { status } = await trpc.queue.getQueueStatus.query(QUEUE_ID);
注意点
  • 複数の SQL をまとめて実行する場合は server/database/transaction.ts の withTransaction() を使い、必要なら FOR UPDATE で行をロックします（entry.insert / entry.insertEvent が実例）。
  • すべて publicProcedure（認証なし）です。認証を入れる場合は middleware で保護されたプロシージャを作ります。
  • 表示用のデータ取得を tRPC に追加すると、リアルタイム同期の恩恵を受けられません。画面に出すデータは Electric の Shape で同期するのが基本です。
