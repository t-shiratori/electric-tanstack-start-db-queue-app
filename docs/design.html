アプリの設計書

この設計書は「どう作られているか」と「なぜそう作ったか」をまとめたものです。 画面ごとの振る舞いは仕様書、プロセスや通信経路はアーキテクチャの解説を参照してください。

対象: main ブランチ データ: PostgreSQL 3 テーブル 状態: イベントから導出

01設計方針

このアプリは「紙の整理券のように止まらず、クラウドサービスのように全端末で状態を共有できる」順番待ちシステムを目指しています。 そのために、次の 5 つの方針で設計されています。

① 状態を保存しない

受付（entry）には「待機中」「呼び出し中」といった状態の列を持たせません。状態の変化をイベントとして追記し、現在の状態は毎回計算します。

② 読み取りと書き込みを分ける

読み取りは Electric による同期、書き込みは tRPC による API 呼び出しと、経路を完全に分離しています。

③ UI はローカルのデータを見る

画面はサーバーに問い合わせず、ブラウザ内の TanStack DB をライブクエリで参照します。操作は楽観的に即時反映されます。

④ 1 アプリで全端末

受付・呼び出し・表示・スマホは同じアプリの別ルートです。端末の違いは「どの画面を開くか」だけで表現します。

⑤ レイヤーを分ける

ドメイン（ビジネスルール）をフレームワークから切り離し、リポジトリのインターフェース越しにインフラを使います。

02データモデル設計

データベースは queue（待ち行列）→ entry（受付）→ entry_event（出来事の記録）の 3 段の親子構造です。 定義は migrations/001_create_tables.sql にあります（002 で既存環境の created_at を TIMESTAMPTZ に変換）。 日時列はタイムゾーン付きの TIMESTAMPTZ で、時刻を「絶対的な瞬間」として保存するため、どのタイムゾーンの端末でも正しい時刻で表示されます。

03イベントソーシング設計

受付の「現在の状態」はどこにも保存されていません。entry（不変の情報）と entry_event（出来事の履歴）を組み合わせ、 最新のイベントの種類から状態を毎回計算します。

状態を持たない理由

よくある設計 entry.status を UPDATE する

  • 2 台の端末が同時に更新すると、後から書いた方が勝ち、先の操作が消える
  • 「いつ・誰が呼び出したか」を残すには別の履歴テーブルが必要
  • 同期中の端末に「行の書き換え」を正しく届ける必要がある

この設計 entry_event を INSERT するだけ

  • 書き込みは常に新しい行の追加なので、同時操作でも行の取り合いが起きない
  • 履歴がそのまま監査ログになり、平均待ち時間なども後から計算できる
  • 同期されるのは「行の追加」だけで、端末側の状態計算は全端末で同じ結果になる

状態の導出ルール

最新イベント（DB）ドメインイベント導出される状態意味

app/domain/entry/state.ts（抜粋）
export function calculateCurrentState(events: EntryEvent[]): EntryState {
  if (events.length === 0) return ENTRY_STATE.WAITING;
  // 作成時刻の新しい順に並べ、先頭（最新）のイベントから状態を決める
  const sorted = [...events].sort((a, b) => b.createdAt.getTime() - a.createdAt.getTime());
  return EVENT_TYPE_TO_STATE[sorted[0].type];
}

この関数はフレームワークに依存しない純粋な関数で、ドメイン層（app/domain）に置かれています。

04状態遷移設計

waitingキャンセルcancelledお客様スマホ

calledキャンセルcancelledお客様スマホ

遷移ルールの検証（3 段構え）

遷移ルールはドメイン層の checkEventAppend()（内部で isValidStateTransition() を使う）に 1 か所だけ定義し、 クライアントとサーバーの両方で同じ関数を使って検証します。

① UIその状態で可能な操作のボタンだけを表示する
② ユースケースaddEntryEvent() がローカルのイベント履歴で判定し、不正なら書き込む前にエラー
③ サーバーentry.insertEvent が受付の行を FOR UPDATE でロックし、DB の履歴で再判定。不正なら CONFLICT

③ により、別端末とのすれ違い（例：スマホでキャンセルした直後に、同期が届く前の呼び出し端末で「完了」を押す）でも不正なイベントは記録されません。 このとき楽観的な変更はロールバックされ、画面には「現在の状態（キャンセル済み）からはこの操作を実行できません」と表示されます。

05読み取りモデル（マテリアライズドビュー）設計

画面が使うデータは、2 つのコレクションから派生させたビューとして React のフックで提供されます（app/query/entry/hooks.ts）。 ビューは保存されず、元データが同期で更新されると自動的に再計算されます。JOIN と状態の計算はアプリ全体で 1 回だけ行い（app/query/entry/entry-states-store.ts）、全フックで結果を共有します。 考え方・更新の流れ・改善案はマテリアライズドビュー解説で詳しく説明しています。

useEntriesByState指定状態の受付useEntryStates を filter（他のフックの元）

06書き込み設計

画面からの書き込みは、すべて TanStack DB のコレクションへの insert として表現されます。 コレクションは画面に即座に反映（楽観的更新）しつつ、裏で tRPC 経由で PostgreSQL に書き込み、 その変更が Electric で戻ってくるまで待ってから確定します。

画面ボタン操作でユースケースを呼ぶ
ユースケースID・トークンを作り、リポジトリに渡す
コレクションinsert() で画面に即反映
onInsert → tRPCサーバーで INSERT し txid を返す
確定待ちawaitTxId(txid) で同期の到着を待つ
app/infrastructure/database/collections.ts（抜粋）
export const entriesCollection = createCollection(
  electricCollectionOptions({
    id: 'entries',
    schema: DbEntrySchema,
    getKey: (entry) => entry.id,
    shapeOptions: { ...electricConfig, params: { table: 'entry' } }, 1
    onInsert: async ({ transaction, collection }) => {
      const { modified: newEntry } = transaction.mutations[0];
      const result = await trpc.entry.insert.mutate({ ... }); 2
      await collection.utils.awaitTxId(result.txid); 3
    },
  }),
);
  1. 1読み取りは Electric の Shape（entry テーブル全体）から同期する。
  2. 2書き込みはサーバーの tRPC プロシージャに任せる。サーバーは同じトランザクション内で pg_current_xact_id() を返す。
  3. 3そのトランザクション ID を含む変更が Electric から届くまで待つ。届いた時点で楽観的な値が同期済みの値に置き換わり、画面がちらつかない。

整理券発行は 2 回の書き込み

createEntry()（app/usecases/entry/create-entry.ts）は、entry の insert と created イベントの insert を順番に行います。 それぞれ tx.when('settled') で完了を待ってから次へ進みます。

2 つの書き込みは 1 つのトランザクションではない

entry の書き込みが成功し、イベントの書き込みが失敗した場合、created イベントのない受付が残ります。 ただし状態の導出ルールで「イベントなし ＝ waiting」としているため、画面上は待機中として扱われ、運用は継続できます。

なぜ Electric に直接書かないのか

Electric は 読み取り専用の同期エンジンで、クライアントから PostgreSQL へ書き込む機能を持ちません。 そのため書き込みは自前の API が担当します。このアプリでは当初 TanStack Start のサーバー関数を使っていましたが、 現在は独立した Hono + tRPC サーバーに移行しています（詳しくはtRPC の技術解説）。

07採番設計

整理券番号は サーバーが INSERT と同じトランザクションの中で決めます。 画面に即時表示するための仮の番号は事前に queue.getNextTicketNumber（MAX(number) + 1）で取得しますが、確定番号は entry.insert の中で次のように採番します。

server/routers/entry.ts（entry.insert の中身）
BEGIN;
SELECT id FROM queue WHERE id = $queue_id FOR UPDATE;      -- 待ち行列の行をロック（同時発行を直列化）
INSERT INTO entry (id, queue_id, number, party_size, public_token, created_at)
  SELECT $id, $queue_id, COALESCE(MAX(number), 0) + 1, $party_size, $token, now()
  FROM entry WHERE queue_id = $queue_id
  RETURNING number, pg_current_xact_id()::text AS txid;
COMMIT;
  • 重複の防止：待ち行列の行のロックで採番を直列化します。UNIQUE(queue_id, number) 制約は最後の安全装置として残しています。
  • 仮の番号と確定番号：楽観的更新では仮の番号を表示し、Electric から同期された行（確定番号）に置き換わります。発行完了モーダルには、リポジトリが同期後のコレクションから読み取った確定番号を表示します。
  • オフライン時：採番にサーバーが必要なため、オフラインでは整理券を発行できません。

08公開トークン設計

お客様のスマホは、整理券の QR コードに含まれる public_token で自分の受付を特定します。URL は https://<LAN の IP>/entry/<token> です。

形式

英大文字と数字の 8 文字（Zod: length(8)・/^[A-Z0-9]+$/）。

使う文字

ABCDEFGHJKLMNPQRSTUVWXYZ23456789 の 32 文字。読み間違えやすい I O 0 1 を除外しています。

組み合わせ数

328 ≒ 1.1 兆通り。推測は困難ですが、生成には Math.random() を使っており暗号論的な乱数ではありません。

10実行環境の設計（SSR とブラウザ）

  • 画面はブラウザでだけ描画する：各ルートは <ClientOnly> で画面を包み、サーバー側では「読み込み中...」だけを返します。TanStack DB と Electric の同期はブラウザでしか動かないためです。
  • 環境変数はブラウザで検証する：env.client.ts が import.meta.env を Zod で検証し、VITE_ELECTRIC_URL は https のみ許可しています。
  • HTTPS が必須：ID の生成に使う crypto.randomUUID() は安全なコンテキスト（HTTPS または localhost）でしか使えません。LAN 内のスマホからも HTTPS でアクセスできるよう、Caddy で TLS を終端します。
