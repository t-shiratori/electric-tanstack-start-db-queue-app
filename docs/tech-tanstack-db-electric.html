TanStack DB × ElectricSQL
技術解説

このアプリが「再読み込みなしで全端末が同じ状態を表示する」のは、 ElectricSQL（PostgreSQL の変更を配る同期エンジン）と TanStack DB（ブラウザ内のリアクティブなデータストア）の組み合わせによるものです。 それぞれの役割と、2 つをつなぐしくみを順に解説します。全体の流れだけを先に見たい場合は05 全体のシーケンスへ。

@electric-sql/client 1.5.28 @tanstack/react-db 1.0.0-rc.1.5 @tanstack/electric-db-collection 1.0.0-rc.1.5

01何を解決しているのか

一般的な Web アプリと、このアプリのデータの取り方を比べると違いがよく分かります。

ElectricSQL の担当

PostgreSQL の変更を検知し、購読しているブラウザへ配る。読み取りの同期だけを行う。

TanStack DB の担当

届いたデータをブラウザ内に保持し、JOIN や絞り込みを差分で再計算する。書き込みを楽観的に反映する。

tRPC（自前 API）の担当

Electric ができない書き込みを受け持つ。詳しくはtRPC の解説へ。

02ElectricSQL のしくみ

Electric は DB ではない：データの置き場所

Electric は名前に SQL と付きますが、データベースではありません。データの「正本」は PostgreSQL にだけあり、 Electric は PostgreSQL の変更をブラウザへ届ける同期エンジン（配達係）です。 たとえるなら、PostgreSQL が本店の台帳、Electric は台帳の変更を写して各店舗に配る配送センターです。

PostgreSQLElectric
役割データベース（正本）同期エンジン（配達係）
持っているデータテーブルの本物のデータPostgreSQL から写した変更のログ（Shape ログ）。配達を効率よくするためのキャッシュ
書き込み受け付ける（INSERT / UPDATE …）受け付けない（読み取り専用）
消えたらデータを失うPostgreSQL から作り直せる（このアプリでは Electric にボリュームを付けていない）
問い合わせ方SQLHTTP（GET /v1/shape?table=…）

データは次の 4 か所にあります。画面（ライブクエリ）が見ているのは ③ ＋ ④ だけで、表示のためにサーバーへ問い合わせることはありません。

場所何があるか寿命
① PostgreSQLentry / entry_event テーブルの本物のデータ永続
② Electric の Shape ログ① の変更を写したログ作り直せるキャッシュ
③ コレクションの同期済みの層② から受け取った行（① の写し）メモリのみ。再読み込みで消え、また ② から取り直す
④ コレクションの楽観的な層まだ確定していない自分の操作確定または失敗するまでの一時的なもの

読み取り：コレクションのデータはどこから来るか

コレクションのデータは、元をたどれば PostgreSQL のデータです。Electric は中継しているだけで、データを作り出してはいません。 また、Electric が送るのは「変わった」という通知ではなく、行のデータそのものです（insert なら全列）。 クライアントは届いたデータをそのまま手元の写しに反映するので、通知を受けてから API に取りに行く、という往復がありません。

書き込み：新規エントリーや受付完了はどこへ行くか

書き込みは Electric を通りません。tRPC サーバーが PostgreSQL に直接書き、その結果が読み取りの経路で全端末に戻ってきます。

新規エントリー（受付端末で整理券を発行）

  1. ReceptionComponent → ユースケース createEntry
  2. entriesCollection.insert()：④ に入り、画面にすぐ出る
  3. onInsert → trpc.entry.insert：サーバーが ① の entry に INSERT（整理券番号もここで決まる）
  4. ① の変更が ② を通って全端末の ③ に届く
  5. 自分の端末では ④ の仮の行が ③ の本物の行に置き換わる

受付完了（呼び出し端末で「完了」）

  1. CallComponent → ユースケース markEntryDone
  2. entryEventsCollection.insert()：done イベントが ④ に入る
  3. onInsert → trpc.entry.insertEvent：サーバーが遷移ルールを確かめて ① の entry_event に INSERT
  4. 以降は新規エントリーと同じ（② を通って全端末の ③ に届く）

docker-compose.yml の Electric にある ELECTRIC_WRITE_TO_PG_MODE は、Electric の古いバージョン向けの設定の名残です。今の Electric（1.x）はクライアントからの書き込みを受け付けません。

論理レプリケーションから Shape へ

Electric は PostgreSQL の論理レプリケーションに接続し、WAL（変更履歴）を読み取ります。 そして、クライアントが購読している Shape（「どのテーブルの、どの行か」という購読単位）ごとに変更をログとして並べ、HTTP で配信します。

PostgreSQL 側のしくみこのアプリでの値役割
パブリケーションelectric_publication_defaultどのテーブルの変更を流すか。購読された entry と entry_event を Electric が自動で登録する
レプリケーションスロットelectric_slot_default（pgoutput）Electric がどこまで読んだかを PostgreSQL 側で覚えておく。Electric が止まっても、再起動後に続きから読める
WALwal_level=logical（docker-compose.yml）行単位の変更を論理レプリケーションで取り出せるようにする設定

Electric は受け取った変更を Shape ごとのログとしてディスクに書き、ログ上の位置を offset で表します。 クライアントは「offset のどこまで受け取ったか」を覚えておき、その続きを HTTP で取りに行きます。 Electric はクライアントごとの状態を持たないので、端末が何台に増えても、同じログを読ませるだけで済みます。

変更が全端末に届くまで：3 つの区間

PostgreSQL でコミットされた変更がブラウザの画面に出るまでには、3 つの区間があります。 区間ごとに、通信のしかたと「どちらから動き始めるか」が違います。 図の値は、このアプリのローカル環境で PostgreSQL の状態（pg_stat_replication / pg_replication_slots）と Electric の応答を実際に確認したものです。

区間 ①：PostgreSQL → Electric（論理レプリケーション）

  1. コミットすると WAL に書かれる：PostgreSQL は、どの変更もまず WAL（先行書き込みログ）に書いてからコミットを完了します。本来は障害から復旧するためのしくみですが、wal_level=logical にすると「どのテーブルの、どの行が、どんな値になったか」を復元できる情報も記録されます。
  2. Electric は「レプリケーション接続」でつながっている：Electric は起動時に、ふつうの SQL 接続とは別にレプリケーション用の接続を張り、「スロット electric_slot_default の続きから、パブリケーション electric_publication_default の変更を流して」と頼みます。PostgreSQL 同士で複製を作るときと同じしくみで、Electric はPostgreSQL の複製先のふりをしています。
  3. PostgreSQL が解読して押し出す：PostgreSQL の中の walsender プロセスが WAL を読み、pgoutput プラグインで行単位の変更に解読して、つなぎっぱなしの接続で Electric へ押し出し（push）ます。届くのはトランザクション単位のまとまりで、コミットされたものだけです（ロールバックしたものは届かない）。
  4. Electric が受け取った位置を報告する：Electric は処理し終えた WAL の位置（LSN）を PostgreSQL に伝え、PostgreSQL はそれをスロットに記録します。Electric が止まっている間も、PostgreSQL は未送信の WAL を消さずに残すので、再起動後に続きから受け取れます。
ローカル環境で確認した PostgreSQL の状態（抜粋）
-- Electric との接続（レプリケーション接続）
SELECT state, sent_lsn FROM pg_stat_replication;
 state     | sent_lsn
 streaming | 0/1A004E8          ← 変更を流し続けている

-- Electric 用のスロット
SELECT slot_name, confirmed_flush_lsn FROM pg_replication_slots;
 slot_name             | confirmed_flush_lsn
 electric_slot_default | 0/1A004F0      ← Electric がここまで受け取った

Electric の中：Shape ログへの振り分け

Electric は届いた変更を、関係する Shape ごとに振り分けます（このアプリでは entry と entry_event）。 そして Electric のメッセージの形（応答の中身）に変換し、Shape ログの末尾に追記します。

  • メッセージの txids には、そのトランザクションの ID が入ります。このアプリが awaitTxId で照合しているのはこの値です。
  • offset の前半は WAL 上の位置（LSN）です。実際の応答の electric-offset: 27263864_0 の 27263864 を 16 進数にすると 0x1A00378、PostgreSQL の表記では LSN 0/1A00378 になります。ブラウザが覚えている offset は、元をたどれば PostgreSQL の WAL の位置です。

区間 ②：Electric → ブラウザ（HTTP ロングポーリング）

ブラウザからは、すでに GET …&offset=27263864_0&live=true が届いていて、Electric はこれを保留しています。 Shape ログに変更が追記されると、Electric はその Shape で保留中のリクエストすべてに「その offset より後のログ ＋ up-to-date」を返します。 同じ offset で待っていた端末にはまったく同じ応答が返るので、端末ごとに中身を作り分ける必要がなく、端末が増えても負担が増えにくい作りです。

この区間は区間 ① と逆で、ブラウザから動き始めています。ブラウザが先に「次の変更をください」と頼んで待っているので、 サーバーは返事を返すだけで、見かけ上は押し出しているのと同じになります（くわしくは次の通信のしくみ）。

区間 ③：ブラウザの中（メモリ内の処理）

  1. ShapeStream（@electric-sql/client）：応答の JSON を読み、electric-schema の型ごとに parser で値を変換して（created_at を Date に、など）購読者に渡します。新しい offset ですぐ次の live=true を送ります。
  2. コレクション（@tanstack/electric-db-collection）：変更メッセージを同期済みの層に書き込み、up-to-date でまとめて確定します。txids を控えて、待っている awaitTxId を完了させます。
  3. ライブクエリ（TanStack DB）：コレクションの変更を受けて、JOIN の結果を差分だけ計算し直します。
  4. entry-states-store.ts → React：状態を 1 回だけ計算し直し、useSyncExternalStore 経由で React に知らせて、変わったコンポーネントだけを再描画します。
区間通信どちらから動き始めるかどこまで受け取ったかの管理
① PostgreSQL → ElectricPostgreSQL のレプリケーションプロトコル（TCP でつなぎっぱなし）PostgreSQL が押し出すスロットの confirmed_flush_lsn
② Electric → ブラウザHTTP GET（ロングポーリング）ブラウザが先に頼んで待つブラウザが覚えている offset
③ ブラウザの中メモリ内の関数呼び出し応答の到着コレクションの同期済みの層

どの区間も「どこまで受け取ったか」を位置で管理しているので、途中で接続が切れても、続きから取りこぼしなく受け取れます。

通信のしくみ：HTTP のロングポーリング

Electric との通信は WebSocket ではなく、ふつうの HTTP GET の繰り返しです。 クライアントライブラリ（@electric-sql/client の ShapeStream）が、次の 4 段階のやり取りを自動で行います。 下の図の URL やヘッダーの値は、このアプリのローカル環境で entry_event の Shape を実際に取得したときのものです。

  • ① 初回：offset=-1（最初から）で取得すると、Shape を作った時点のテーブルの全行（スナップショット）が insert メッセージとして返り、最後に snapshot-end が付きます。応答ヘッダーの electric-handle がこの Shape の ID、electric-offset が次に読む位置です。
  • ② 追いつき：受け取った handle と offset で続きを取得します。スナップショットを作った後にコミットされた変更が、ログからまとめて届きます。最後にup-to-date（ここまでで最新）が付きます。TanStack DB はこの up-to-date を受け取った時点でコレクションを ready にします。
  • ③ ライブ（変更なし）：live=true を付けると、Electric は新しい変更が来るまで応答を保留します。20 秒たっても変更がなければ、up-to-date だけを返します。
  • ④ ライブ（変更あり）：保留中に PostgreSQL でコミットがあると、Electric はその場で応答を返します。クライアントは新しい offset ですぐ次の live=true を送るので、常に 1 本のリクエストが待ち受けている状態が続きます。これが「サブスクライブ（購読）」の正体です。
クエリパラメータ意味
table同期するテーブル。このアプリでは entry と entry_event（コレクションの shapeOptions.params で指定）
offsetShape ログのどこまで受け取ったか。-1 は最初から
handleShape の ID。① の応答ヘッダーで受け取り、以降のリクエストに付ける
livetrue でライブモード（変更が来るまで保留する）。up-to-date を受け取ってから付ける
cursorライブ応答の electric-cursor の値。キャッシュ（CDN など）に古い応答を返させないための値
where / columns行と列の絞り込み。このアプリでは使っていない（全行・全列を同期）

応答の中身：メッセージとヘッダー

応答の本文はメッセージの JSON 配列です。行の変更を表す「変更メッセージ」と、同期の区切りを表す「制御メッセージ」の 2 種類があります。

② 追いつきの応答（一部・実際の値）
[
  {
    "headers": {
      "operation": "insert",                // insert / update / delete
      "relation": ["public", "entry_event"],
      "txids": [813],                       // この変更をコミットしたトランザクション ID
      "lsn": "27243560", "op_position": 0, "last": true
    },
    "key": "\"public\".\"entry_event\"/\"5101dbf2-…\"",
    "value": {                                // 行の値（すべて文字列で届き、型変換はクライアント側）
      "id": "5101dbf2-…", "entry_id": "20dacb30-…", "type": "created",
      "actor": "staff", "device_id": null, "created_at": "2026-11-22 14:29:00.2079+00"
    }
  },
  /* … 変更メッセージが続く … */
  { "headers": { "control": "up-to-date" } }   // 制御メッセージ：ここまでで最新
]

snapshot-endスナップショットの終わり。どのトランザクションまで含むか（xmin / xmax）を示すスナップショットの範囲として記録する

購読が続くしくみ：再接続・作り直し・一時停止

タイムアウト20 秒で区切ってつなぎ直す

1 本の HTTP リクエストを開きっぱなしにしないため、変更がなくても 20 秒で応答が返ります。クライアントはすぐ次を送るので、利用者から見ると途切れません。

通信エラー待ち時間を延ばしながら再試行

サーバーに届かないときは、1 秒 → 2 秒 → 4 秒 … と待ち時間を 2 倍にしながら（最大 32 秒）無期限に再試行します。復旧すれば、覚えている offset の続きから受け取るので、取りこぼしはありません。

409Shape の作り直し

Electric 側で Shape が作り直されると、古い handle へのリクエストに 409 と新しい handle が返ります（must-refetch）。コレクションはデータを空にして ① から取り直します。

タブ見えていない間は一時停止

ブラウザのタブが非表示になると（document.hidden）購読を一時停止し、表示されたら続きから再開します。表示端末のように常に前面に出している画面では止まりません。

クライアントには、ライブモードを SSE（Server-Sent Events）で受け取るオプション（liveSse）もありますが、既定はロングポーリングで、このアプリもロングポーリングを使っています。 コレクションごとに 1 本ずつ購読するため、1 つのタブから entry と entry_event の 2 本のリクエストが常に待ち受けています（Caddy の HTTPS は HTTP/2 なので、1 つの接続にまとめて送られます）。

コレクションが変更を受け取るまで

electricCollectionOptions は、コレクションの同期が始まると ShapeStream を作り、stream.subscribe() でメッセージを受け取ります。 届いたメッセージは、次のようにコレクションの同期済みの層へ反映されます。

受信ShapeStream が 1 回の応答に含まれるメッセージの配列をまとめて渡す
書き込み変更メッセージを同期トランザクションに書き込む（begin → write）。txids も控えておく
確定up-to-date が来たらまとめてコミットする。途中の状態が画面に出ることはない
通知コレクションの変更がライブクエリに伝わり、差分だけ再計算される
照合控えた txid で、待っている awaitTxId(txid) を resolve する
  • 同期が始まるのは、コレクションを使うライブクエリなどが購読したときです（既定の同期モード eager では、そのとき Shape の全行を取得します）。
  • 同期済みの層は Electric から届いたデータだけで作られ、楽観的な変更はその上に重ねて見せているだけです（03 コレクション）。

Electric は「書き込み」をしない

Electric は PostgreSQL → クライアントの一方向の同期だけを担当します。クライアントからの書き込みは、アプリ自身の API（このアプリでは tRPC）で PostgreSQL に書き、その結果が Electric 経由で戻ってくる、という設計になります。

03TanStack DB のしくみ

コレクション：同期データ ＋ 楽観的な変更

コレクションは、型付きのオブジェクトの集まりです。データの入り口（同期元）は差し替え可能で、このアプリでは Electric を使う electricCollectionOptions を使っています。画面から見えるのは、同期済みのデータに、まだ確定していない楽観的な変更を重ねたものです。

ライブクエリ：差分だけ再計算する

ライブクエリは SQL に似たクエリビルダーで、複数のコレクションの JOIN・絞り込み・並べ替えを書けます。 コンポーネントの中で作る useLiveQuery と、モジュールで作って共有する createLiveQueryCollection があり、このアプリは後者で 1 つだけ作っています。 結果は「一度計算して終わり」ではなく、元のコレクションに変更が入るたびに影響を受ける部分だけが再計算されます（差分データフロー）。

app/query/entry/entry-states-store.ts（共有ライブクエリ）
const joinedEntryEventsQuery = createLiveQueryCollection({
  id: 'joined-entry-events',
  query: (query) =>
    query
      .from({ entry: entriesCollection })
      .leftJoin({ event: entryEventsCollection },
        ({ entry, event }) => eq(entry.id, event.entry_id))   // 受付 × イベント
      .select(({ entry, event }) => ({
        id: entry.id, ticketNumber: entry.number, token: entry.public_token,
        eventType: event?.type, eventCreatedAt: event?.created_at, /* … */
      }))
      .orderBy(({ entry }) => entry.number, 'asc'),
});

このアプリでは JOIN の結果を受付ごとにまとめ、calculateCurrentState() で状態を計算しています。この計算は変更 1 回につき 1 回だけ行い、結果を useSyncExternalStore で全フックに配ります。 JOIN と並べ替えまでは TanStack DB の差分計算、そこから先（状態の計算・統計）は JavaScript 側の計算という分担です（詳しくはマテリアライズドビュー解説）。

楽観的更新とトランザクション

collection.insert() を呼ぶとトランザクションが作られ、変更はすぐに楽観的な層に入ります。 その後、コレクションに設定した onInsert（ミューテーションハンドラー）が実行され、その結果でトランザクションの行き先が決まります。

リポジトリ実装（electric-entry-repository.ts など）は await tx.when('settled') で、このトランザクションの完了を待っています。 成功すれば resolve、失敗すれば元のエラーで reject されるため、ユースケースの try / catch でエラーを画面に伝えられます。

042 つをつなぐ：txid による確定待ち

楽観的な変更は「いつ消すか」が重要です。サーバーへの書き込みが終わった瞬間に消すと、 その変更がまだ Electric から届いていない場合、一瞬だけデータが消えて画面がちらつきます。 これを防ぐのが txid（トランザクション ID）による照合です。

txid の受け渡し

サーバーINSERT と同じトランザクションで pg_current_xact_id() を取得して返す
PostgreSQLコミットすると WAL にそのトランザクション ID が記録される
Electric変更メッセージのヘッダーに txids を付けて配信する
コレクションawaitTxId(txid) が一致する txid を見つけたら resolve
server/routers/entry.ts（insert の抜粋）
const inserted = await withTransaction(ctx.pool, async (client) => {
  await client.query('SELECT id FROM queue WHERE id = $1 FOR UPDATE', [queue_id]); // 採番を直列化
  const result = await client.query(
    `INSERT INTO entry (id, queue_id, number, party_size, public_token, created_at)
     SELECT $1, $2, COALESCE(MAX(number), 0) + 1, $3, $4, now() FROM entry WHERE queue_id = $2
     RETURNING number, pg_current_xact_id()::text AS txid`,
    [id, queue_id, party_size, public_token],
  );
  return InsertedEntryRowSchema.parse(result.rows[0]);   // txid は z.coerce.number() で数値に
});
return { txid: inserted.txid, number: inserted.number, success: true };
app/infrastructure/database/collections.ts（抜粋）
onInsert: async ({ transaction, collection }) => {
  const { modified: newEntry } = transaction.mutations[0];   // 楽観的に入れた値
  const result = await trpc.entry.insert.mutate({ /* … */ }); // サーバーに書く
  await collection.utils.awaitTxId(result.txid);             // 同期で戻るまで待つ
},

awaitTxId の既定のタイムアウトは 15 秒です。Electric が止まっているなど、txid が届かない状態が続くとエラーになり、トランザクションは failed（ロールバック）になります。 このとき PostgreSQL への書き込み自体は成功している点に注意してください（Electric が復旧すれば同期で表示されます）。

05全体のシーケンス

ここまでの部品がどの順番で動くのかを、1 枚のシーケンス図にまとめます。 受付端末で起動してから、ある受付を「呼び出す」と、その結果が別の端末（表示端末など）に届くまでの流れです。

  1. 1起動・初回同期：画面がライブクエリを購読すると、元になるコレクションが Electric への購読を始めます。スナップショット（Shape を作った時点の全行）→ 追いつき（その後の変更）と取得し、up-to-date を受け取った時点で ready になって画面に一覧が出ます。
  2. 2待機：各端末は live=true のリクエストを送り、Electric は変更が来るまで応答を保留します。20 秒たっても変更がなければ空の応答を返し、端末はすぐ次のリクエストを送ります。
  3. 3操作：「呼び出す」を押すと entryEventsCollection.insert() が楽観的な層に called イベントを入れ、サーバーを待たずに画面が変わります。
  4. 4書き込み：onInsert が tRPC の entry.insertEvent を呼びます。サーバーは受付の行をロックして遷移ルールを検証し、INSERT してコミットし、そのトランザクションの txid を返します。コレクションは awaitTxId(txid) で同期を待ちます。
  5. 5配信：コミットは WAL に記録され、論理レプリケーションで Electric に届きます。Electric は保留していたすべての端末の応答に、この変更（txids 付き）を載せて返します。
  6. 6確定・次の待機：操作した端末では txid が一致して awaitTxId が終わり、楽観的な行が同じ ID の同期済みの行に置き換わります（表示は変わらず、ちらつかない）。他の端末では行が追加されて画面が再描画されます。どの端末も、応答に含まれる新しい offset で次の live=true を送ります。

サーバーが遷移ルールに合わないと判断した場合（別の端末が先に完了にしていたなど）は、④ で tRPC が CONFLICT エラーを返します。 このとき onInsert が失敗し、トランザクションは failed になって楽観的な行は消え、画面は元に戻ります。⑤ 以降は起きません。 受付の発行（entriesCollection.insert()）も、サーバーが整理券番号を採番する点を除けば同じ流れです。

07つまずきやすいポイント

SSRコレクションはブラウザ専用

コレクションと Shape の購読はブラウザで動きます。TanStack Start の SSR で実行されないよう、各ルートは <ClientOnly> で画面を包んでいます。

HTTPS安全なコンテキストが必要

ID 生成の crypto.randomUUID() は HTTPS（または localhost）でしか使えません。スマホから IP アドレスでアクセスする場合も Caddy の HTTPS を通します。

日時TIMESTAMPTZ と parser

Electric は列の型名ごとに parser を適用し、指定がなければ文字列のまま渡します。日時列を TIMESTAMP（タイムゾーンなし）にすると UTC の時刻がオフセットなしで届き、ブラウザがローカル時刻と解釈して時刻がずれます。このアプリは列を TIMESTAMPTZ にし、"…+00" 形式を ISO 8601 に整形する parsePgTimestamp() で Date にしています（そのままの形式は Safari などで解釈できない場合がある）。

同期範囲Shape はテーブル全体

Shape に where を指定していないため、全端末が全行を同期します。データが増えると初回同期が重くなるので、将来は日付やトークンで絞り込む余地があります。

永続化再読み込みで再同期

同期データはメモリ上にあるため、ページを再読み込みすると Shape を最初から取り直します。オフライン中は書き込みもできません。

APIRC 版の API 変更

TanStack DB 1.0 RC への更新で、完了待ちが tx.isPersisted.promise から tx.when('settled') に、onInsert の戻り値（{ txid }）が awaitTxId() の呼び出しに変わりました。
